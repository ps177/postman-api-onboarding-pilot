# postman-api-onboarding-pilot

Automated onboarding of a customer API into Postman from its OpenAPI spec, using Postman's CSE-managed GitHub Actions. Built for the Postman CSE case study.

- **Service onboarded end to end:** Payment Refund API (`specs/payment-refund-api-openapi.yaml`), Lambda/API Gateway, GitHub Actions
- **Second service analysed:** Claims Processing API (mixed Lambda/ECS, GitLab CI), see [ADAPTATION_ANALYSIS.md](ADAPTATION_ANALYSIS.md)
- **Full debugging record:** [BUILD_LOG.md](BUILD_LOG.md)

---

## 1. What this does

One manually triggered workflow (`.github/workflows/onboard-service.yml`) takes a service's OpenAPI spec and produces, in a real Postman Enterprise workspace:

| Output | Result for Payment Refund API |
|---|---|
| Workspace | `[PAY] payment-refund-api` |
| Spec in Spec Hub | `payment-refund-api` |
| Collections generated from the spec | `[Baseline]` (6 requests, no tests), `[Smoke]` (6 requests, 18 tests), `[Contract]` (6 requests, 36 tests) |
| Environments | `prod`, `uat`, `qa`, `dev`, each with its `baseUrl` |
| Collections exported to this repo | `postman/collections/` (v3 YAML, kept in sync by the action) and `postman/exports/` (v2.1 JSON snapshot) |
| Environments exported to this repo | `postman/environments/*.postman_environment.json` |
| Mock server | `payment-refund-api Mock`, on the Baseline collection |
| Monitor | `payment-refund-api - Smoke Monitor`, on the Smoke collection (created paused) |
| CI workflow | `.github/workflows/ci.yml`, generated by the action, fixed by hand (see §6) |
| State file | `.postman/resources.yaml`, maps repo files to Postman cloud IDs |

Both onboarding runs (#1 and #2) completed green against a real workspace using my own Postman API key. Every artifact above was verified inside Postman and GitHub, not inferred from the job status.

## 2. How the actions chain together

```
workflow_dispatch (inputs: service name, spec URL, envs, base URLs)
        │
        ▼
postman-api-onboarding-action@v0   (orchestrator)
        │
        ├── postman-bootstrap-action
        │     fetch spec from raw URL → lint → create/find workspace
        │     → upload spec to Spec Hub → generate Baseline/Smoke/Contract
        │     → create environments
        │
        └── postman-repo-sync-action
              export collections + environments to repo → write .postman/resources.yaml
              → create mock (Baseline) + monitor (Smoke) → link workspace to repo
              → commit "chore: sync Postman artifacts and metadata" with the PAT
```

I call the orchestrator, not bootstrap and repo-sync separately, because the pitch to the platform team is "one step per service". The two lower-level actions remain the fallback when a specific stage needs debugging.

## 3. How I built it and the decisions I made

**Starter asset: bypassed the wrapper, kept the input pattern.** I validated `starter-assets/` against the upstream v0 README and found five problems:

1. `spec-url` is wired to `inputs.spec-path`, so a file path is sent where a URL is expected.
2. The workflow sits in `starter-assets/workflows/`, which GitHub never executes.
3. Only `github.token` is passed. There is no `gh-fallback-token`, so the action cannot push workflow files or write repo settings.
4. No `environments-json`, so it would default to `["prod"]` while the spec defines four environments.
5. `postman-access-token` is optional, which risks a silent partial success.

The composite wrapper added no logic, only an extra layer to debug, so I call the upstream action directly. I kept the starter's one good idea: `workflow_dispatch` inputs, so the same file onboards any service by changing inputs only.

**Inputs added beyond the starter, each for a reason found during the build:**

| Input | Why |
|---|---|
| `environments-json: ["prod","uat","qa","dev"]` | Match the four servers in the spec |
| `env-runtime-urls-json` | Run #1 left `baseUrl` empty in every environment; the spec's `servers` were not applied. Passing URLs explicitly fixed it in run #2 |
| `generate-ci-workflow: 'false'` | The generated `ci.yml` was invalid and I fixed it by hand. Without this flag, every rerun would regenerate and overwrite the fix |
| `gh-fallback-token` (fine-grained PAT) | `GITHUB_TOKEN` cannot push files under `.github/workflows/` |

**Spec handled as-is.** I found 12 issues in the payment spec (see BUILD_LOG) and did not fix them. A CSE should not silently change a customer's contract; the issues go back to the owning team as feedback.

**Repo topology.** One pilot repo holding all three specs, but only one service onboarded into it. The reason: `.postman/resources.yaml` holds exactly one workspace ID, so a second service in the same repo would collide with the first. For scale, see §8.

## 4. Run instructions

**Prerequisites**
1. Postman Enterprise trial (the actions use features not on free plans).
2. Repo secrets:
   - `POSTMAN_API_KEY`: a Postman API key (PMAK).
   - `POSTMAN_ACCESS_TOKEN`: run `postman login`, then `cat ~/.postman/postmanrc | jq -r '.login._profiles[].accessToken'`. **This token expires.** Refresh it before any run.
   - `GH_FALLBACK_TOKEN`: fine-grained PAT scoped to this repo, read/write on Actions, Contents, Secrets, Variables and Workflows.
3. The spec must be reachable at a raw HTTPS URL (this repo is public for that reason).

**Run**
1. Actions → **Onboard Service to Postman** → **Run workflow**.
2. Defaults are set for the payment service. For another service, change the inputs (name, spec URL and path, domain, domain code, environments, base URLs).
3. Runtime is about 1.5 to 4 minutes; spec linting takes most of it.

**Rerun behaviour**
- Idempotent. Run #2 reused workspace `7376447b…`, refreshed the three collections in place (stable IDs), reused the existing mock and monitor, and created no duplicates.
- State comes from the committed `.postman/resources.yaml`, not from repo variables as the exercise brief describes. If that file is deleted or missing on a branch, the next run creates a **duplicate** workspace.

- [x] Spec visible in Spec Hub
- [x] Three collections with the expected requests; tests present in request-level post-response scripts
- [x] Four environments with `baseUrl` populated (after run #2)

- [x] Mock server live: `GET https://f904fc03-cbb4-4015-b01f-f4df19bd7f36.mock.pstmn.io/v2/health` returns the spec's `healthy` example (the `/v2` base path is required)
- [x] Monitor exists, paused, with one run per onboarding run

**Why the tests are red, and why that is expected.** The spec's servers (`*.payments.example.com`) do not exist. The monitor history shows the debugging story clearly:

| Monitor run | Error | Meaning |
|---|---|---|
| After onboarding #1 | `REQUEST` Invalid URI `http:///refunds/...` | `baseUrl` empty: our configuration problem |
| After onboarding #2 | `NETWORK` getaddrinfo ENOTFOUND `api.payments.example.com` | URL now correct; the host does not exist: a customer dependency |

**Supplementary check (not the end-to-end proof).** To confirm the generated tests themselves execute correctly, I created a manual `mock` environment pointing `baseUrl` at the mock server and ran `[Contract]` in the Collection Runner: **36/36 passed**. This only proves the wiring and test scripts work. The mock returns the spec's own examples, so the spec is effectively being checked against itself. It is not evidence that the real API conforms.

## 6. Issues encountered (summary)

Full detail in [BUILD_LOG.md](BUILD_LOG.md).

1. **Generated CI was invalid.** `ci.yml` line 43 used `if: secrets.X != ''`; GitHub rejects `secrets` in `if:`. The onboarding job was green, but the CI it generated could never run. Fixed with a two-line change (expose the secret as job-level `env`, test `env.X`), then protected with `generate-ci-workflow: 'false'`.
2. **Empty `baseUrl`.** Spec servers were not applied to environments. Fixed with `env-runtime-urls-json`.
3. **Green job, failing tests.** The action runs tests with `set +e` and puts results in an artifact. A green onboarding job does not mean tests passed.
4. **Contract tests pass vacuously** when a request errors: the scripts `return` early when there is no response, so headers/body/schema checks report PASS without checking anything. Pass counts alone are misleading.
5. **"00 - Resolve Secrets" runs last.** It is meant to fetch auth from AWS Secrets Manager before the other requests, but it is ordered last in the Smoke and Contract collections (confirmed in the runner, the YAML export and the JSON export). In a real run, no request would get a token.
6. **State not in repo variables** (see §4).
7. **Trial limitations:** "Team feature is not available" (sub-teams) and a requester-invite error because the requester and key owner are the same person.
8. **GitHub annotations are truncated.** The UI showed about 10 per step; the downloaded logs had 52 lint warnings.

## 7. What the generated checks can infer from the spec, and what they can't

| From the spec alone (automatic) | Needs service-specific knowledge |
|---|---|
| Each endpoint exists and returns a status code the spec defines | A refund cannot exceed the original payment |
| Error responses carry `error`, `message`, `code`, `timestamp` (these schemas declare `required`) | Only `captured` transactions can be refunded; 180-day limit; max 5 refunds per transaction |
| `status` is one of the five allowed values; `refundId` matches `^rfnd_` | A real captured `transactionId` to test against |
| Field types and Content-Type | Order of operations: create, then check status, then cancel only while pending |
| Response time under a threshold (Smoke) | Side effects: a refund actually reaching the payment gateway |
| | Valid credentials and how to obtain them |

Two limits worth knowing:
- **Success schemas declare no `required` fields**, so a 200 response missing `refundId` would still pass the contract. Error schemas are strict; success schemas are not.
- **Business rules live in description text**, which no generator can turn into assertions.

**Why this matters operationally.** The generated tests are a cheap, immediate baseline: they catch dead endpoints, breaking contract changes and spec drift on every run, for every onboarded service, with no one writing tests. They do not tell anyone the service makes correct business decisions. That layer has to come from the service team, so the plan assigns it explicitly: the platform team owns the generated baseline; each service team owns its business-rule tests, added to the same collections.

## 8. What's universal vs what changes per service

| Universal (same for every service) | Changes per service (workflow inputs) | Needs platform-team coordination |
|---|---|---|
| The workflow file and `postman-api-onboarding-action@v0` | Project name, domain, domain code | Real base URL per environment |
| Bootstrap → repo-sync chain | Spec raw URL and path | Auth credentials usable by automation |
| Three collection types and naming (`[CODE] service`) | Environment list (payments: 4, claims: 3) | Network path for monitors/CI to reach private APIs |
| `generate-ci-workflow` and base-URL handling | Base URL per environment | CI platform (GitHub Actions vs GitLab) |
| Validation checklist and rerun behaviour | | Test data; which environment CI may target |

The Claims analysis shows that for a service on different infrastructure and a different CI system, the workflow itself changes only in its inputs; everything else is coordination. See [ADAPTATION_ANALYSIS.md](ADAPTATION_ANALYSIS.md).

**Recommended topology at scale.** One reusable workflow in a central template repo (`workflow_call`), and a thin caller workflow in each service repo, next to that service's spec. Each service repo then has its own `.postman/resources.yaml`, which avoids the one-workspace-per-repo collision and keeps the spec with the code that changes it.

## 9. What the customer's platform team must configure

Things I could not do without their AWS account, GitLab access or network:

1. **Base URLs** for every environment of every service.
2. **Automation credentials:** a service-account JWT or OAuth client-credentials (the payment spec only offers `authorizationCode`, which needs a human in a browser).
3. **Secrets Manager:** secrets named `api-credentials-<env>` in the right region (the generated environments hardcode `eu-west-2`), plus a scoped IAM identity Postman can use to read them.
4. **Network reachability:** the monitor runs on Postman's cloud runner (US East), which cannot reach APIs inside a private VPC. Options: a Postman private runner, or running the collections with the Postman CLI on their own CI runners.
5. **CI target environment:** generated CI targets **prod** on every push and every 6 hours, and the Smoke/Contract collections include `POST /refunds` and `POST /cancel`. Against real prod this would create real refunds. CI should target dev or qa; anything touching prod must be read-only.
6. **Ownership of scheduled checks:** the 6-hour CI cron and the monitor overlap. Pick one.
7. **Service accounts** for the Postman API key and GitHub token instead of personal credentials, plus a rotation process for `POSTMAN_ACCESS_TOKEN`.
8. **For GitLab teams:** a runner, CI variables, and a way for onboarding to fetch the spec (see the adaptation analysis).
9. **Test data** such as a captured `transactionId`.

## 10. Trade-offs

- **Bypassed the starter wrapper:** one less layer to debug, at the cost of not matching the provided scaffold.
- **Hand-fixed `ci.yml` plus `generate-ci-workflow: 'false'`:** the fix survives reruns, but the repo will not receive future CI template updates. The bug should be reported upstream.
- **Pinned to `@v0`:** matches the exercise materials; newer versions exist with different inputs and token handling, and would need re-validation before adoption.
- **Spec not fixed:** tests are only as strict as the spec, so known gaps stay visible rather than hidden.
- **Base URLs passed as an input** duplicate what is in the spec's `servers`; this is a workaround for v0 behaviour.
- **Personal credentials and a public repo:** fine for a pilot, not for production.
- **JSON exports are a manual snapshot** (`postman/exports/`); the action keeps only the v3 YAML in sync. This could be automated with `GET /collections/{uid}` from the Postman API.
- **The `mock` environment used for the 36/36 run was created by hand** and is not part of the automation.
